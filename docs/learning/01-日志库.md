# 学习总结：日志库（lg）

## 开发时序：第 1 步

### 为什么从日志库开始？

任何稍大的 Go 项目，第一个需要的通用基础设施就是 **日志**。没有日志，调试和追踪就是黑盒操作。

本项目的日志库并非从零开发，而是从已有的成熟实现（`../agent-study/llmLib/lg/`）vendor 进来，做 Go 风格适配后直接使用。

**核心原则**：不重复造轮子，好的基础设施直接复用。

---

## 概念解释

### 日志库要解决什么问题？

想象你在开发一个后端服务，程序可能在凌晨 3 点崩溃。你第二天早上来上班，需要搞清楚：
- 崩溃发生在哪个模块？（`user` 服务？`order` 服务？）
- 发生了什么操作？（查询用户？支付回调？）
- 错误的上下文是什么？（`userID=123, amount=99.9`）
- 在代码哪一行？（`service.go:42`）

一个合格的日志库需要回答上面全部问题，并且：
- 输出到不同目标（控制台、文件、同时输出）
- 按级别过滤（开发时看 DEBUG，生产环境只看 ERROR）
- 格式统一，便于阅读和搜索

## 架构设计

```
┌─────────────────────────────────────┐
│           包级别便捷函数              │  ← 用户直接调用 lg.Info("...")
│   Debug/Info/Warn/Error/Fatal        │
├─────────────────────────────────────┤
│             Logger                   │  ← 可创建的实例，绑定 module + fields
│   Module("module") / With(fields)    │
├─────────────────────────────────────┤
│             Entry                    │  ← 一条日志记录：时间、级别、模块、文件、消息、字段
├─────────────────────────────────────┤
│           Writer 接口                │  ← 输出目标：ConsoleWriter / FileWriter
│   Write(*Entry) error / Level()     │
├─────────────────────────────────────┤
│            Router                    │  ← 按模块名路由到不同 Writer
│   Route("module", writer)           │
└─────────────────────────────────────┘
```

## 关键设计

### 1. Writer 接口：输出与存储分离

```go
type Writer interface {
    Write(entry *Entry) error
    Level() Level       // 此 Writer 能接受的最低日志级别
    Close() error       // 优雅关闭（如关闭文件）
}
```

这是一个经典的 **策略模式**：
- `ConsoleWriter`：输出到 `os.Stdout` 或自定义 `io.Writer`
- `FileWriter`：输出到文件，自动创建目录
- `MultiWriter`：同时广播到多个 Writer

**关键决策**：为什么 Writer 要带 `Level()` 而不是让 Logger 单独判断？
→ 每个 Writer 可以有自己的最低级别。比如控制台只显示 WARN 以上，文件记录全部 DEBUG。

### 2. Router：按模块分流

```go
type Router struct {
    defaultWriter Writer          // 未匹配到路由时的默认输出
    routes        map[string]Writer // module → Writer 映射
    mu            sync.RWMutex     // 并发安全
}

router := lg.NewRouter(consoleWriter)
router.Route("db", fileWriter)    // db 模块写文件
router.Route("api", multiWriter)  // api 模块同时写控制台和文件
```

**关键决策**：为什么需要 Router？
→ 大型项目中，不同模块的日志可能需要不同的存储策略。DB 查询日志写大文件按月归档，API 请求日志即时输出到控制台。

### 3. Logger 分层：默认 Logger + 模块 Logger + 字段 Logger

```go
// 1. 包级别便捷函数（默认 Logger）
lg.Info("服务启动", lg.Fields{"port": 8080})

// 2. 模块 Logger（自动带上模块名）
dbLog := lg.Module("db")
dbLog.Info("连接成功", lg.Fields{"host": "localhost"})
// 输出: [INFO] [db] 连接成功 database.go:15 host=localhost

// 3. 带固定字段的 Logger（多次调用共享字段）
userLog := lg.Module("user").With(lg.Fields{"userID": 123})
userLog.Info("登录")
userLog.Warn("权限不足")
// 每条日志都自动带上 userID=123
```

**关键决策**：为什么不用全局 Logger？
→ 包级别便捷函数对于简单场景很方便，但在复杂模块中，`lg.Module("db")` 创建的子 Logger 能自动带上模块名，不需要每次调用都传。

### 4. Entry：日志记录的结构化

```go
type Entry struct {
    Time    time.Time // 2024-01-15 10:30:45
    Level   Level     // INFO / WARN / ERROR
    Module  string    // "db"
    File    string    // "database.go:42"
    Message string    // "连接成功"
    Fields  Fields    // {"host": "localhost", "port": 5432}
}
```

输出格式：`[INFO] [db] 连接成功 database.go:42 host=localhost port=5432`

**关键决策**：为什么用 `Fields map[string]any` 而不是结构化参数？
→ Go 没有变长泛型参数，`map[string]any` 是传递任意键值对最自然的方式。它牺牲了一点类型安全，换来了极大的灵活性。

## 思想总结

| 思想 | 体现 |
|------|------|
| **不重复造轮子** | 从已有成熟实现 vendor，而非从头写 |
| **关注点分离** | Entry（数据）→ Writer（输出）→ Router（路由）→ Logger（API） |
| **接口驱动** | Writer 接口让 Console/File/Multi 实现可互换 |
| **渐进增强** | 简单场景用包函数，复杂场景用 Module/With 链式调用 |
| **并发安全** | Router 用 RWMutex，MultiWriter 用 Mutex |

这个日志库的设计模式是典型的 Go 风格：**接口 + 组合 + 链式调用**，不依赖任何继承或反射。
