# 学习总结：AI 层 — 核心类型定义

## 开发时序：第 2 步

### 为什么这是第二步？

底层基础设施（日志）就绪后，需要开始构建业务层。AI Agent 的最底层是 **LLM 交互**。无论你的 Agent 多么智能，它最终都是调用某个大语言模型的 API。AI 层就是封装这个交互的。

**核心目的**：定义一套 **统一接口**，屏蔽 30+ 个 LLM 提供商（OpenAI、Anthropic、Google 等）的差异，让上层 Agent 代码不需要关心底层是哪个提供商。

---

## 开发思路：先抽象，后具体

```
Step 1: 定义核心类型（Message、ContentBlock）   ← 本文件
Step 2: 定义事件系统（Event、Stream）            ← 本文件
Step 3: 定义接口（Model、Provider）              ← 本文件
Step 4: 实现第一个 Provider（OpenAI）            ← 下一篇文章
```

这种 **先画图纸再盖房** 的思路，确保接口设计是"由需求驱动"而非"由实现驱动"。

## 核心类型

### 1. Role：谁在说话

```go
type Role string

const (
    RoleSystem    Role = "system"    // 系统提示词
    RoleUser      Role = "user"      // 用户消息
    RoleAssistant Role = "assistant" // AI 回复
    RoleTool      Role = "tool"      // 工具执行结果
)
```

这是 LLM 对话的基本"角色"模型。为什么需要区分角色？因为 LLM 在生成回复时，需要知道每句话是谁说的——system 是"行为规范"，user 是"任务"，assistant 是"历史回复"，tool 是"工具返回的数据"。

### 2. Message：一条消息

```go
type Message struct {
    Role    Role           // 谁说的
    Content []ContentBlock // 内容（可能包含文字、工具调用等）
}
```

**关键决策**：Content 是 `[]ContentBlock` 而不是 `string`。

因为 LLM 的回复不仅仅有文字。它可能说"我需要查一下天气"，同时调用 `get_weather("北京")` 工具。

```
┌─────────────────────────────────────────────────────┐
│ Role: Assistant                                     │
│ Content:                                            │
│   [TextBlock] "我需要查一下北京的天气"               │
│   [ToolCallBlock] get_weather(city="北京")           │
└─────────────────────────────────────────────────────┘
```

### 3. ContentBlock：一条消息中的一块内容

```go
type ContentBlockType int

const (
    ContentText     ContentBlockType = iota  // 纯文本
    ContentThinking                           // 思考过程（部分模型支持）
    ContentToolCall                           // 工具调用
    ContentImage                              // 图片
)

type ContentBlock struct {
    Type     ContentBlockType
    Text     string       // 文本内容
    ToolCall *ToolCall    // 工具调用（当 Type == ContentToolCall 时）
    ImageURL string       // 图片 URL（当 Type == ContentImage 时）
}
```

**关键决策**：为什么用 `flat struct + Type` 字段，而不是 Go 的 `interface{}` 联合类型？

```go
// ❌ Go 没有原生 union type，用 interface 会很麻烦
type ContentBlock interface { ... }
type TextBlock struct { ... }
type ToolCallBlock struct { ... }

// ✅ flat struct 更 Go 风格，且序列化/反序列化友好
type ContentBlock struct {
    Type     ContentBlockType
    Text     string
    ToolCall *ToolCall
}
```

这种设计在 Go 社区被称为 "tagged union via flat struct"——用类型标签 + 可选字段模拟联合类型。

### 4. ToolDefinition & ToolCall：工具

```go
type ToolDefinition struct {
    Name        string         // 工具名称
    Description string         // 工具描述（给 LLM 看的）
    Parameters  map[string]any // 参数 JSON Schema
}

type ToolCall struct {
    ID        string         // 调用 ID（LLM 生成）
    Name      string         // 工具名称
    Arguments map[string]any // 调用参数
}
```

LLM 通过 `ToolDefinition` 理解"我能用什么工具"，然后通过 `ToolCall` 发起调用。Agent 运行时拿到 `ToolCall` 后执行真正的工具逻辑，把结果回传给 LLM。

### 5. Context：对话上下文

```go
type Context struct {
    Messages   []Message        // 历史消息
    Tools      []ToolDefinition // 可用工具列表
    MaxTokens  int              // 最大输出 token 数
    Temperature float64         // 随机性（0~2）
}
```

这是 `Model.Chat()` 方法的输入参数。它封装了一次 LLM 调用需要的全部信息。

## 事件系统

### 为什么需要事件系统？

LLM 的回复是 **流式的**（一个字一个字往外蹦），不是一次性全部返回。为什么？

```
HTTP 请求 → LLM 计算 → 回复
                        ↓
              传统模式: 等待全部计算完再返回（可能 5-10 秒）
                        ↓
              流式模式: 算出一个字就返回一个字（用户感觉"秒回"）
```

流式模式体验好得多，但编程实现更复杂。你不能简单 `response, err := model.Chat(...)`，而是需要一个 **事件流** 来传递每个增量。

### Event 设计

```go
type EventType int

const (
    EventStart          EventType = iota  // 对话开始
    EventTextStart                       // 一段文本开始
    EventTextDelta                       // 一个文本增量（可能是一个字）
    EventTextEnd                         // 一段文本结束
    EventThinkingStart                   // 思考过程开始
    EventThinkingDelta                   // 思考过程增量
    EventThinkingEnd                     // 思考过程结束
    EventToolCallStart                   // 工具调用开始
    EventToolCallDelta                   // 工具调用增量（arguments 逐步构建）
    EventToolCallEnd                     // 工具调用结束
    EventDone                            // 对话完成
    EventError                           // 发生错误
)

type Event struct {
    Type     EventType
    Delta    string      // 文本增量
    ToolCall *ToolCall   // 工具调用（完整或部分）
    Usage    *Usage      // Token 用量统计
    Error    error       // 错误信息
}

type Usage struct {
    PromptTokens     int
    CompletionTokens int
    TotalTokens      int
}
```

### Stream：Go channel 的妙用

```go
type Stream <-chan Event  // 只读 channel
```

Go 的 channel 天然适合流式场景：

```go
stream := model.Chat(ctx, context)
for event := range stream {  // 阻塞等待下一个事件，channel 关闭时自动退出
    switch event.Type {
    case EventTextDelta:
        fmt.Print(event.Delta)  // 实时打印
    case EventToolCall:
        // 处理工具调用
    case EventDone:
        // 完成
    case EventError:
        // 出错
    }
}
```

**关键决策**：为什么用 channel 而不是回调函数？
→ channel + `for...range` 是 Go 惯用的迭代模式，读起来像同步代码，执行时是异步的。比回调函数（callback hell）清晰得多。

## Model 和 Provider 接口

### Provider：既是目录，也是入口

```go
type Provider interface {
    ID() string                      // "openai"
    Name() string                    // "OpenAI"
    Models() []ModelInfo             // 列出所有可用模型
    Model(id string) (Model, error)  // 获取指定模型
    Chat(ctx context.Context, context Context) Stream  // 直接聊天（使用默认模型）
}
```

### Model：一个具体的语言模型

```go
type ModelInfo struct {
    ID       string           // "gpt-4o"
    Name     string           // "GPT-4o"
    Provider *ProviderInfo    // 所属提供商
}

type Model interface {
    Info() ModelInfo
    Chat(ctx context.Context, context Context) Stream
}
```

**关键决策**：为什么 Provider 和 Model 是分开的接口？

```
OpenAI 提供商
├── GPT-4o        (Model)
├── GPT-4o-mini   (Model)
├── GPT-4         (Model)
└── o3-mini       (Model)
```

一个提供商会提供多个模型。Provider 是"目录"，Model 是"目录中的一款产品"。这种分层让代码结构清晰：

```go
prov := openai.New(config)
model, _ := prov.Model("gpt-4o-mini")  // 选择便宜的小模型
stream := model.Chat(ctx, context)      // 直接用模型对话
```

## 思想总结

| 思想 | 体现 |
|------|------|
| **先抽象后具体** | 先定义接口，再实现 OpenAI，确保接口由需求驱动 |
| **Go 惯用模式** | flat struct + Type 标签替代 interface union；channel 替代回调 |
| **流式优先** | 从 Event 系统到 Stream 类型，全部围绕流式交互设计 |
| **最小接口** | Provider 只有 4 个方法，Model 只有 2 个，够用即可，不提前设计 |
