# 构建、打包、发布流程

## 概述

企业级但轻量的构建-打包-发布方案，通过 Git Tag 触发 CI，自动交叉编译 + GitHub Release。

---

## 一、版本策略

[Semantic Versioning](https://semver.org/)，版本号唯一来源是 **git tag**，不在代码中硬编码。

| 变更类型 | bump | 示例 |
|---------|------|------|
| Bug 修复 | patch | v1.0.0 → v1.0.1 |
| 新功能（向后兼容） | minor | v1.0.0 → v1.1.0 |
| 破坏性变更 | major | v1.0.0 → v2.0.0 |

---

## 二、构建方案

### 2.1 平台矩阵

| OS | Arch | 说明 |
|----|------|------|
| darwin | arm64 | Apple Silicon Mac ✅ |
| windows | amd64 | Windows 桌面 ✅ |

> 文档保留全平台参考：`linux/amd64` `linux/arm64` `darwin/amd64`，按需扩展。

### 2.2 ldflags 注入

编译时注入版本元信息（`-s -w` 去除调试符号缩小体积）：

```bash
go build -ldflags "
    -s -w
    -X main.version=v1.0.0
    -X main.commit=$(git rev-parse --short HEAD)
    -X main.buildDate=$(date -u +%Y-%m-%dT%H:%M:%SZ)
" -o pg ./cmd/pg/
```

`pg version` 输出：

```
pg version v1.0.0
  commit:    abc1234
  built:     2026-08-01T12:00:00Z
  go:        go1.26.5
```

`cmd/pg/main.go` 中 `version`/`commit`/`buildDate` 是 `var`（默认值 `"dev"`/`"none"`），发布时通过 ldflags 覆盖。

### 2.3 产物命名

```
pg_v1.0.0_darwin_arm64.tar.gz
pg_v1.0.0_windows_amd64.zip
```

## 三、文件清单与说明

### 3.1 `.goreleaser.yaml`

goreleaser 发布配置，Git Tag 推送后由 CI 自动执行：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `builds.goos` | `[darwin, windows]` | 目标操作系统 |
| `builds.goarch` | `[amd64, arm64]` | 目标架构 |
| `builds.ignore` | `darwin/amd64`, `windows/arm64` | 排除不构建的组合 |
| `builds.ldflags` | `-s -w -X main.version={{.Version}} ...` | 版本号注入 |
| `builds.env` | `CGO_ENABLED=0` | 静态链接 |
| `archives.formats` | `[tar.gz]`（Windows 覆盖为 `[zip]`） | goreleaser v2 语法 |
| `archives.name_template` | `{{.ProjectName}}_{{.Version}}_{{.Os}}_{{.Arch}}` | 产物命名 |
| `archives.files` | `LICENSE` | 附带许可证 |
| `checksum.name_template` | `checksums.txt` | SHA256 校验文件 |
| `changelog` | commit 自动生成 | Release 底部简要列表（排除 docs/test/ci） |
| `release.header` | 安装命令 | Release 正文，自动从 commit changelog 生成 |
| `release.draft` | `false` | 直接发布 |
| `release.prerelease` | `auto` | 自动判断 pre-release |

### 3.2 `.github/workflows/ci.yml`

每次 push/PR 到 main 触发：

| Job | 触发条件 | 内容 |
|-----|---------|------|
| `lint` | push/PR main | `go run golangci-lint@v1.64`（Go 版本由 `go.mod` 决定） |
| `test` | push/PR main | `go vet` + `go test -race`（Go 版本由 `go.mod` 决定） |

> 使用 `go-version-file: go.mod` 自动对齐 Go 版本，无需手动维护版本号。

### 3.3 `.github/workflows/release.yml`

Git Tag `v*` 推送时触发：

| Job | 触发条件 | 内容 |
|-----|---------|------|
| `goreleaser` | tag `v*` | `actions/checkout@v5` → `setup-go@v6`（`go-version-file: go.mod`）→ `goreleaser/goreleaser-action@v7`（`version: '~> v2'`） |

需要权限：`contents: write`（创建 Release）

### 3.4 `Makefile`

统一开发/构建/发布命令入口：

**编译、打包、发布**

| 命令 | 步骤 | 说明 |
|------|------|------|
| `make build` | `go build -ldflags ...` | 本地发布构建，ldflags 注入最新 tag 和 commit |
| `make pack` | `./pack.sh` | 手动交叉编译打包（不依赖 CI） |
| `make release` | `git push origin main --tags` | 推送 tag 触发 CI 自动发布 |

**代码检查**

| 命令 | 步骤 | 说明 |
|------|------|------|
| `make lint` | `golangci-lint run ./...` | 静态代码检查 |
| `make test` | `go test -race -count=1 ./...` | 全量测试 + 竞态检测 |

**发布 tag 版本管理**

| 命令 | 步骤 | 说明 |
|------|------|------|
| `make version` | `git tag --sort=-v:refname \| head -1` | 查看当前最新 tag |
| `make next-version` | 交互式输入 → `git tag` | 输入新版本号并打 tag |

**其他**

| 命令 | 步骤 | 说明 |
|------|------|------|
| `make run` | `go build -o pg ./cmd/pg/ && ./pg` | 本地编译并运行（dev 版本号） |
| `make clean` | `rm -rf pg pi dist/` | 清理构建产物 |
| `make help` | grep 注释 | 显示所有命令帮助 |

### 3.5 `pack.sh`

本地手动打包脚本（不依赖 CI/goreleaser），`./pack.sh [版本号]`：

| 步骤 | 操作 |
|------|------|
| 1 | 取版本号：参数 > `git describe --tags` > `dev` |
| 2 | 交叉编译 `darwin/arm64` → `dist/pg` |
| 3 | 打包 `dist/pg_{版本号}_darwin_arm64.tar.gz` |
| 4 | 交叉编译 `windows/amd64` → `dist/pg.exe` |
| 5 | 打包 `dist/pg_{版本号}_windows_amd64.zip` |
| 6 | 生成 `dist/checksums.txt`（SHA256） |
| 7 | 清理临时二进制 |

### 3.6 `install.sh`

用户一键安装脚本，自动检测 OS/Arch 从 GitHub Releases 下载预编译二进制：

| 步骤 | 操作 |
|------|------|
| 1 | 检测 `uname -s` / `uname -m` → OS/Arch |
| 2 | 构建下载 URL：`github.com/Effortful-lion/pi-go/releases/{latest|v1.0.0}/download/pg_{os}_{arch}.tar.gz` |
| 3 | `curl` 或 `wget` 下载压缩包到临时目录 |
| 4 | `tar xzf` 解压 |
| 5 | 复制 `pg` 到 `$GOPATH/bin` 或 `$HOME/go/bin` |
| 6 | `chmod +x` 设置可执行 |
| 7 | 输出版本信息，PATH 未包含时给出提示 |

环境变量 `PI_GO_VERSION` 可指定版本（默认 `latest`）。

### 3.7 `uninstall.sh`

卸载脚本，删除 `$GOPATH/bin/pg` 和 `$HOME/go/bin/pg`。

### 3.8 `.gitignore`

忽略的生成文件：

| 类型 | 文件 |
|------|------|
| 编译产物 | `pg` `pi` `*.exe` `*.test` |
| goreleaser | `dist/` |
| 日志 | `logs/` |
| IDE | `.idea/` `.vscode/` `*.swp` `*.swo` |
| OS | `.DS_Store` `Thumbs.db` |

### 3.9 `LICENSE`

MIT 许可证。

### 3.10 `cmd/pg/` 源码结构

| 文件 | build tag | 说明 |
|------|-----------|------|
| `main.go` | 无 | 公共代码：`printVersion()` `printHelp()` `main()` `initLogging()` |
| `main_unix.go` | `!windows` | Unix 子命令路由：`run()` `runChatCmd()` |
| `main_windows.go` | `windows` | Windows 子命令路由：基础命令（config/version/help） |
| `chat.go` | `!windows` | 交互模式：`runChat()` `runSinglePrompt()` `ChatFlags` |
| `config.go` | 无 | 配置结构体 + YAML 加载/保存 |
| `config_cmd.go` | 无 | `config` 子命令（init/show/set） |

## 四、发布流程

### 4.1 确定版本号

```bash
make version                           # 查看最新 tag
# → latest tag: v1.0.0
```

按 semver 规则判断 bump：

| 变更 | bump | 示例 |
|------|------|------|
| fix | patch | v1.0.0 → v1.0.1 |
| feat | minor | v1.0.0 → v1.1.0 |
| breaking | major | v1.0.0 → v2.0.0 |

### 4.2 发布操作

```bash
make next-version    # 交互式输入 v1.0.1 并打 tag
make release         # 推送 tag 触发 CI
```

Git 不允许重复 tag，无需担心覆盖。

### 4.3 CI 自动执行流程

```
make release → git push --tags
  │
  ├─ CI (lint + test)     # 每次 push 都跑
  │   ├─ go run golangci-lint@v1.64
  │   └─ go vet + go test -race（Go 版本由 go.mod 决定）
  │
  └─ Release Job           # 仅 tag 触发
      ├─ goreleaser 交叉编译 darwin/arm64 + windows/amd64
      ├─ 打包 tar.gz/zip + checksums.txt
      ├─ 创建 GitHub Release（自动 changelog + 安装命令）
      └─ 上传构建产物
```

# 日志库扩展计划

## 概述

当前 lg 库已支持基本日志输出（Console/File/Multi/Router）和动态文件名（LogNamePattern）。计划扩展以下能力，全部可插拔、可组合。

## 扩展功能

### 1. 定时切割（RotateByInterval）

按时间间隔自动创建新日志文件，避免单文件过大。

```go
// 每小时切割
lg.SetPath("logs", lg.LevelInfo,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02").Char("_").Clock("15"),
    lg.RotateByInterval(time.Hour),
)

// 每天切割
lg.RotateByInterval(24 * time.Hour)

// 每分钟切割（调试用）
lg.RotateByInterval(time.Minute)
```

实现思路：
- 内部维护一个定时器 goroutine
- 到达间隔时，关闭当前文件，下次 Write 时 LogName 自然产生新文件名
- 可插拔：不传该选项时不做定时切割（仅依赖 LogName 自然切换）

### 2. 文件大小限制（RotateBySize）

单文件超过指定大小时自动切换新文件。

```go
// 超过 100MB 切割
lg.RotateBySize(100 * 1024 * 1024)

// 超过 10MB 切割
lg.RotateBySize(10 << 20)
```

实现思路：
- 每次 Write 后累计字节数
- 超过阈值时关闭当前文件，下次 Write 时切换
- 可与 RotateByInterval 组合（任一条件触发）
- 切换时文件名追加序号：`pg_2026-08-01.001.log`, `pg_2026-08-01.002.log`

### 3. 按日志级别分目录（LevelDir）— 默认功能

**默认行为**：`SetPath` 自动按日志级别分目录，无需额外配置。目录名使用 level 的小写字符串。

```
logs/
├── debug/
│   └── pg_2026-08-01.log
├── info/
│   └── pg_2026-08-01.log
├── warn/
│   └── pg_2026-08-01.log
├── error/
│   └── pg_2026-08-01.log
└── fatal/
    └── pg_2026-08-01.log
```

```go
// 默认：自动按级别分目录
lg.SetPath("logs", lg.LevelDebug,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02"),
)
```

**关闭分级目录**：如果不需要分级，显式关闭。

```go
lg.SetPath("logs", lg.LevelInfo,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02"),
    lg.LevelDirOff(),  // 关闭分级，所有级别写到同一目录
)
```

**自定义目录名**：覆盖默认的目录名映射。

```go
// 自定义 error 和 fatal 合并到 error 目录
lg.SetPath("logs", lg.LevelInfo,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02"),
    lg.LevelDirName(lg.LevelFatal, "error"),  // fatal 也写到 error/
)
```

实现思路：
- `SetPath` 内部根据传入的 level 参数自动创建对应子目录
- 每个 level 对应一个独立的 FileWriter，指向不同子目录
- 底层使用 MultiWriter 组合所有级别的 FileWriter
- 每个级别的 FileWriter 共享同一个 LogNamePattern

### 4. 定时清理（Retention）

定期删除过期日志文件，控制磁盘占用。

```go
// 保留最近 7 天的日志
lg.Retention(7 * 24 * time.Hour)

// 保留最近 30 天，每小时检查一次
lg.Retention(30*24*time.Hour, lg.CheckInterval(time.Hour))

// 按文件数量保留：最多 100 个文件
lg.RetentionMaxFiles(100)

// 按总大小保留：最多 1GB
lg.RetentionMaxSize(1 << 30)
```

实现思路：
- 启动后台 goroutine 定期扫描日志目录
- 按修改时间删除超过保留期的文件
- 或按文件数量/总大小，删除最旧的文件
- 只删除由当前 FileWriter 产生的文件（通过文件名前缀匹配，避免误删）

### 5. 日志级别优先级（LevelPriority）— 已废弃

> `SetPath` 的 `level` 参数已覆盖此需求：
> - `lg.SetPath("logs", lg.LevelWarn, pattern)` → 只输出 warn/error/fatal
> - `lg.SetPath("logs", lg.LevelDebug, pattern)` → 输出全部级别
>
> 无需额外实现。

## API 设计

`SetPath` 签名：`func SetPath(dir string, level Level, pattern *LogNamePattern, opts ...LogOption) error`

```go
// 最简用法
lg.SetPath("logs", lg.LevelInfo,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02"),
)

// 全功能用法
lg.SetPath("logs", lg.LevelInfo,
    lg.NewLogNamePattern().Module().Char("_").Date("2006-01-02"),

    // 分级目录（可选）
    lg.WithLevelDir(lg.LevelError, "error"),

    // 切割策略（可选）
    lg.WithRotateByInterval(time.Hour),
    lg.WithRotateBySize(100 << 20),

    // 清理策略（可选）
    lg.WithRetention(7 * 24 * time.Hour),
)
```

- 所有 Option 独立生效，可任意组合

## 实现优先级

| 优先级 | 功能 | 理由 |
|--------|------|------|
| P0 | LevelDir | 日志分类，便于监控告警 ✅ |
| P0 | RotateByInterval | 定时切割 ✅ |
| P0 | RotateBySize | 防止单文件膨胀 ✅ |
| P1 | Retention | 磁盘空间管理 ✅ |
| ~~P2~~ | ~~LevelPriority~~ | 已被 SetPath level 参数覆盖，废弃 |

## 内部实现要点

- 所有扩展通过 `FileWriter` 内部组合实现，不修改 Writer 接口
- 切割/清理的 goroutine 在 `Close()` 时优雅退出
- 文件名序号使用 `.000` 三位补零格式，兼容字典序排序
- 所有配置通过 `FileWriterOption` 函数传入构造函数
# goreleaser 发布修复计划

## 背景

当前仓库在发布阶段出现 `goreleaser release` 报错，需要重点排查：

- `goreleaser` 配置语法是否与 CI 中固定版本兼容
- GitHub Actions 中 action 版本与语法是否有效
- 发布环境中的 Go 代理/依赖下载是否会影响 release

## 已确认事实

- 本地已安装 `goreleaser 2.17.1`
- CI 工作流固定 `goreleaser/goreleaser-action@v7`，并指定 `version: '~> v2.8'`
- 使用本地 `goreleaser 2.17.1` 执行 `goreleaser check` 通过
- 使用本地 `goreleaser 2.17.1` 执行 `goreleaser release --snapshot --clean` 通过
- 使用 `go run github.com/goreleaser/goreleaser/v2@v2.8.0 check` 通过
- 使用 `go run github.com/goreleaser/goreleaser/v2@v2.8.0 release --snapshot --clean` 通过
- 当前机器默认 `GOPROXY=https://goproxy.cn,direct`，在拉取 `goreleaser v2.8.0` 依赖时出现过 `504 Gateway Timeout`，改用 `https://proxy.golang.org,direct` 后恢复

## 当前判断

现有 `.goreleaser.yaml` 本身不是一个可稳定复现的语法错误源，至少对 `2.8.0` 和 `2.17.1` 都成立。

更可能的风险点有两类：

1. CI 运行环境问题
   - GitHub Actions runner 对 action 主版本或 Node runtime 的兼容性
   - 依赖拉取、缓存或代理行为差异
2. 发布链路稳定性问题
   - `goreleaser` 固定到较老次版本，后续维护成本较高
   - 文档、配置和工作流描述存在不一致，容易误导后续排障

## 拟修改内容

1. 收敛 release workflow 版本声明
   - 评估是否将 `version: '~> v2.8'` 调整为 `version: '~> v2'`
   - 保留 `goreleaser-action@v7`
   - 视需要补充更明确的 Go 依赖缓存/版本读取配置
2. 对齐文档与实际配置
   - 修正文档中仍然描述旧版 `setup-go 1.23`、`release.header_file` 等已过时内容
3. 补充变更日志
   - 记录本次 `goreleaser` / release workflow 修复内容

## 预期结果

- GitHub Release 工作流配置更稳，不再依赖过窄的 `goreleaser` 次版本范围
- `goreleaser` 配置、workflow、设计文档三者一致
- 后续再排查 release 失败时，能更快区分“配置错误”和“环境问题”
