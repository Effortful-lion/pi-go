## 2026-08-02

### TUI 迁移至 Bubbletea 框架（最终方案：Enter 换行 + Esc 提交，InputStrategy 可插拔）
- **动机**：废弃 kitty keyboard protocol（方案 A），因其不被 macOS Terminal.app 支持；换用 Bubbletea 实现 100% 跨平台多行输入
- **方案演进**：Double Enter（废弃，无法支持末尾多空行）→ Esc 提交（最终）
- **可插拔设计**：`tui/input.go` 新增 `InputStrategy` 接口，解耦"换行"与"提交"的交互逻辑，库使用者可自行实现策略
  - `EscSubmitStrategy`（默认）：Enter 换行 + Esc 提交
  - 可自定义：Enter 直接提交（单行模式）、Ctrl+Enter 提交等
  - `ChatUI` 通过 `WithInputStrategy()` option 注入策略
- **新增依赖**：`github.com/charmbracelet/bubbletea`、`github.com/charmbracelet/bubbles/textarea`、`github.com/charmbracelet/lipgloss`
- `tui/model.go`（新增）：`ChatModel` Bubbletea Model 定义，实现 `Init`/`Update`/`View`，管理 textarea、历史记录、流式状态；按键路由：Enter→换行、Esc→提交、↑↓→历史、Ctrl+L→清屏、Ctrl+C/D→退出
- `tui/stream.go`（新增）：`agent.Stream` → `tea.Cmd` 适配层，`handleStream()` 流式消费 Agent 事件并累积渲染到 `output` builder
- `tui/chat.go`（重构）：`ChatUI.Run()` 改为创建 `tea.Program` 并启动，删除 `renderAgentStream()` 和手动 raw mode 循环，保留 `ExportConversation`/`truncate`
- `tui/terminal.go`（清理）：删除约 800 行代码（`EnterRawMode`/`LineEditor`/`ReadLine`/`readKey`/`readEscapeSeq`/`parseKittyKey`/`trimCSI`/`keySeq`/所有光标控制函数），仅保留颜色样式函数 + `ClearScreen` + `esc` 常量 + `maxHistory`
- `tui/terminal_test.go`（更新）：删除 `TestUtf8ByteLen`/`TestTrimCSI`/`TestParseKittyKey`，保留 8 个样式测试
- `tui/chat_test.go`（更新）：适配新的 `ChatModel` API，测试 `handleStream` 流式渲染和 `handleEnter` 逻辑
- `docs/spec/终端换行问题.md`（更新）：完整设计文档，记录方案演进（kitty → Double Enter → Esc 提交）和最终架构
- **交互变更**：
  - Enter → 换行（插入 `\n`，永远不提交）
  - Esc → 提交消息
  - 粘贴（Bracketed Paste）→ 直接写入 textarea，绕过 Enter 提交逻辑，防误触
  - 历史浏览 → ↑↓ 键
  - Ctrl+L → 清屏
  - Ctrl+C → 退出
  - Ctrl+D → 输入为空时退出，否则删除字符

### 重构：Provider 请求构造从 map[string]any 迁移到 struct
- **动机**：openai/anthropic/google 三个 provider 的 `buildRequest()` 使用 `map[string]any` 硬编码字段名，类型不安全、IDE 不友好
- **改造内容**：
  - **openai**：新增 `chatRequest`/`chatMessage`/`toolCallMsg`/`toolCallFunc`/`toolDef`/`toolDefFunc` 请求 struct；重命名响应 struct `oaiChunk`→`messageChunk`、`oaiToolCallChunk`→`toolCallChunk`、`toolCallAcc`→`toolCallAccumulator`
  - **anthropic**：新增 `chatRequest`/`chatMessage`/`contentBlock`/`toolDef` 请求 struct；`parseSSE` 中 4 个匿名 struct 提取为 `sseContentBlockStart`/`sseContentBlockDelta`/`sseContentBlockStop`/`sseMessageDelta` 命名 struct
  - **google**：新增 `chatRequest`/`chatContent`/`chatPart`/`funcCall`/`funcResponse`/`systemInstruction`/`toolDef`/`funcDecl`/`generationConfig` 请求 struct；重命名响应 struct `geminiChunk`→`messageChunk`、`geminiContent`→`chatContent`、`geminiPart`→`chatPart`、`geminiFuncCall`→`funcCall`，请求和响应共用类型
- **命名统一**：三个 provider 的相同概念使用一致的命名风格（与 my-openai 对齐）：
  - 请求体：`chatRequest`
  - 消息：`chatMessage`
  - 工具定义：`toolDef`
  - SSE chunk：`messageChunk`
  - 工具调用 chunk：`toolCallChunk`
  - 累积器：`toolCallAccumulator`

### MarkdownLine 改为有状态版本，正确处理跨行代码块
- **问题**：`MarkdownLine` 是无状态函数，无法感知跨行的 ` ``` ` 代码块状态，导致代码块内的行被错误地当作普通 Markdown 渲染（如 `# comment` 变成标题、`*ptr` 变成斜体）
- **方案**：新增 `MarkdownLineRenderer` struct，跟踪 `inCodeBlock`/`codeLang`/`codeLines` 状态
  - `NewMarkdownLineRenderer()` 创建渲染器
  - `RenderLine(line string) string`：逐行渲染，代码块内部原样输出，代码块结束时调用 `Highlight()` 一次性高亮
  - `Reset()`：重置状态（新对话轮次开始时调用）
  - 旧的 `MarkdownLine()` 函数保留向后兼容
- `ChatModel` 新增 `mdLine *MarkdownLineRenderer` 字段，在 `flushLine`/`flushInline` 中调用 `m.mdLine.RenderLine(line)` 替代原来的 `MarkdownLine(line)`
- `handleSubmit` 中调用 `m.mdLine.Reset()` 重置渲染器状态
- 新增 `tui/markdown_test.go`：10 个测试覆盖代码块状态机、嵌套代码块、未关闭代码块、Reset、混合内容、向后兼容等场景
